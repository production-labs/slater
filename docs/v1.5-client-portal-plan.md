### Finding: pin internal-only flag isn't server-persisted

Regular workback line items store their internal-only flag on the item itself
(`d.internal`, persisted into `projects.data`, autosaved). But schedule-day/milestone
**pins** store internal-only in `localStorage` only
(`slater_pin_<key>_<pinId>`, see `public/app.js` ~line 3012/3022) — it never syncs to
the server. That's invisible today because Word doc generation runs client-side in the
same browser that set the flag.

A server-driven client portal can't replicate this: there's no server-side source of
truth for "is this pin internal" to filter on. **Before the portal's timeline/schedule
view can be trusted, pin internal-only needs to move into `projects.data`**, the same
way regular items already work. Small, no schema change, but touches the milestone/pin
rendering code in `app.js`.

### Auth / link design (recommended)

- Each project gets a unique random token: `projects.portal_token` (text, unique,
  nullable — null means the portal isn't enabled for that project).
- Optional password, producer-set: `projects.portal_password_hash` (bcrypt, nullable —
  null means no password required). The mockup shows no login screen, so "optional" is
  the right default, not "required."
- URL shape: `https://slater.productionlabs.io/portal/<token>`.
- A correct password sets a short-lived signed cookie scoped to that project, so repeat
  visits don't re-prompt. This stays fully decoupled from the existing `express-session`
  / `requireAuth` system used for producer logins — no shared session store, no risk to
  the real auth path.

### Draft data model additions

- `projects.portal_token` text unique, nullable
- `projects.portal_password_hash` text, nullable
- `projects.portal_enabled_at` timestamptz, nullable
- New table `portal_updates(id, project_key, owner_id, author, body, created_at)` —
  a real table rather than another JSONB array, for the same reason contacts moved out
  of JSONB in the v2 rewrite: queryable, no full-blob rewrite per post.
- New table `portal_deliverables(id, project_key, owner_id, filename, r2_key, uploaded_at)`,
  backed by a **new** R2 bucket (e.g. `slater-deliverables`), reusing the S3 client
  pattern already proven in `backup/backup.js` / `routes/adminBackups.js`. Do not reuse
  the `slater-backups` bucket — different retention/access needs.
- Per workback item, in `projects.data`: `owner: "producer" | "client"` — drives both
  the "Waiting on you" band and the timeline dot coloring.
- Per schedule day / URL link item, in `projects.data`: `visible_to_client: boolean`,
  **default false** (opt-in, not opt-out — safer default for anything client-facing).

### Draft routes

Public, unauthenticated (new router, explicitly NOT mounted behind `requireAuth`):
- `GET /portal/:token` — portal page shell (new `public/portal.html` + `public/portal.js`,
  same pattern as `login.html`)
- `GET /api/portal/:token` — JSON payload, password-gated by cookie, explicit field
  allowlist (never just forward whatever `/api/projects` returns)
- `POST /api/portal/:token/unlock` — password check, sets the signed cookie
- `POST /api/portal/:token/approve` — marks a "waiting on you" item done
- `GET /api/portal/:token/deliverables/:id` — presigned R2 download, same short-TTL
  pattern as `routes/adminBackups.js`

Producer-side, behind existing `requireAuth`:
- Enable/disable portal, set/clear password
- Post an update
- Toggle `visible_to_client` / `owner` on items
- Upload a deliverable
